## 一句话结论

完整功能源码已经统一进入仓库根目录。AI 采用“一次视觉生成、最多一次纯文本格式修复、五个已校验展示板块、运行期真实深度思考”；舌象与面部观察共用分层 Prompt 和独立 Markdown 知识库。制作板块源码现有 Agent、爆款复刻与 Agent 内的数字人口播，生成计划使用 `production-plan.v3`，支持字幕模板、逐句时间轴、随包贴纸和卡片式导出微调。Android Media3 只执行通过校验的计划。2026-08-20 在 API 35 x86_64 AVD 上，签名 Release instrumentation 已用真实 H.264/AAC 竖屏夹具产出带 cues、贴纸和浮动文字的蒙太奇成片，以及保留原声的数字人切片成片；这是模拟器 Media3 证据，不是物理真机通过。项目只使用根项目目录和 Release APK 交付路径，版本唯一来源是 `android/app/build.gradle.kts`；构建成功后按版本号分别归档，不覆盖旧 APK。当前源码与下载页均为已完成公网文件回验的 `v0.1.18`/`versionCode=26`。`v0.1.18` 已完成主机 Release 构建、签名、归档、上传与公网哈希核对；物理设备上的制作主链仍待用户端测，因此只能称为已公开的 Release 安装包，不得表述为真机通过。

AI 运行反馈是两条简单 AI Flow，不是 Agent、工具调用循环或动态编排器。诊察与内容拆解在正常路径各发出一次结构化流式请求；同一响应中的五个顶层字段或字段组完整闭合后，先通过对应 Zod 与业务语义校验，再发送 `structured-generation-progress.v1` 安全投影。完整文档无效时最多进行一次格式修复，诊察修复为纯文本且不再次发送私有图片。板块进度和推理文本都不持久化；WebView 或进程退出后不恢复半成品，用户重试会重新生成完整文档，只有完整 `diagnosis-report.v1` / `content-analysis.v1` 校验并原子保存后才成立。

任务列表、任务详情、内容拆解与观察报告在健康状态下通过按 ID 或窄变更事件自动更新。权威记录先落盘再通知页面；初始异步列表读取会回放读取期间到达的 upsert、delete 或报告终态，并拒绝更早请求的迟到结果，因此不需要固定轮询或手动刷新。只有读取或订阅失败时保留“重新读取”恢复动作。

  端侧验收发现一个阻断缺陷并已修：TypeScript 用容差判断整毫秒，Kotlin 用位精确的 `% 1.0 == 0.0`，于是 `8.005` 秒（IEEE-754 下是 8004.999999999999 毫秒）能通过校验落盘、却让渲染永久失败，且错误被兜底成可重试的合成失败。`ProductionPlanParser.secondsToMs` 改为四舍五入加同样的容差——原先的位精确判断连 `8.1` 秒都会拒绝，截断取整还会丢 1 毫秒。同时给 `ERR_INVALID_ARGUMENT` 建了映射，渲染器拒绝计划不再伪装成可重试的合成失败。其余修复：用户输入错误统一报 `PRODUCTION_PLAN_EDIT_INVALID` + `edit_input` 并按字段给准确提示（此前语速、音量、主文字越界都会被报成「字幕生成不出来」，模板与素材错误还会被报成 AI 输出问题、把用户引去重跑 AI）；微调与生成计划受同一条禁止照搬来源原文的约束；选了背景音乐时音量必须大于 0，取消音乐时不接受同时设置音量；只含零宽字符的口播按空内容拒绝，不会烧进一条看不见的字幕；私有文件删除失败映射为 `STORAGE_WRITE_FAILED`，不再向界面抛出无码的原生异常。

  有三条机器校验的硬约束：每个分镜必须至少引用一条真实证据 id，引用不存在的 id 会被拒绝并只修一次（仍失败报 `AI_FORMAT_REPAIR_FAILED`）；说不出画面时必须交空清单加 `emptyReason`，给了分镜就不能同时声明证据不足；脚本草稿与制作计划受**同一条**原创约束——为此把「连续 12 字照搬」抽成共享的 `sharesVerbatimRun`，把证据 id 校验抽成共享的 `assertEvidenceRefs`，拆解流程改为调用同一份实现，避免两处规则各自漂移。另外，「不能为空」按**看得见的字符**判定：`emptyReason`、复刻思路、画面描述、素材说明与脚本草稿只要只剩零宽或其他不可见字符就按空拒绝，避免用户面对一片空白却以为系统给过了内容——判定抽成 `packages/core` 的 `hasVisibleText`，制作计划微调（服务端与微调页）现在读同一份，界面不再接受服务端必然拒绝的输入。没有证据单元时直接按 `TASK_ARTIFACT_MISSING` 失败，不白花一次模型调用。`karaoke_glow` 在这一层必然降级：蓝图阶段还没有任何录音，逐字时间无从谈起，降级来源记在 `degradedFromTemplateId`。

  时长冲突按「以清单为准」解决而不是把用户拉回四档：`ProductionService.create` 本来就接受 15 到 60 之间的任意整数，四档只是制作首页的控件，所以 `startProject` 直接用清单建议秒数的合计当目标时长（例如 37 秒的清单就建 37 秒的项目）。清单少于 3 镜或合计越界时**不建项目**，当场说明原因——本地合成至少要 3 个画面，先建一个注定失败的项目只是把失败推后。

  绑定是真的，不是打勾：`ProductionAsset.requirementOrder` 落在项目记录上，`importAssets(projectId, { requirementOrder })` 一次只收一个素材，并在**打开系统选择器之前**就把「这次是给第几项选的」写进 `project.json`，因此外部 Activity 导致 WebView 重建后回来的文件仍然知道自己属于哪一项。同一项已有素材时拒绝再绑（先移除再换），两个素材占同一项的记录读盘时直接判损坏。删素材即解绑：界面不另存一份「哪项已完成」，完成状态一律从素材上读。

  代码审查发现这个待绑定标记会活得太久：选择器带走 WebView 后取消或失败，进程内的清理没有机会跑，标记留在盘上，制作页之后**不带清单项**的普通导入就会被静默算成上一项已完成——界面显示第 3 项已绑定，成片第 3 镜用的却不是为它拍的东西。现在的规则是「标记只描述当前正在进行的那一次选择」：不带清单项的导入在打开选择器前先清掉遗留标记，带清单项的导入直接覆盖它，因此任何一次导入都不会继承上一次的归属。新增回归单测直接在盘上留一个过期标记，断言随后的普通导入不带 `requirementOrder`、且标记被清掉。

  规划器必须尊重绑定：`ProductionPlanningAsset.requirement` 把该镜的画面意图、素材说明和建议秒数一起送进提示词，`validateProductionPlan` 再硬校验**镜头数等于已绑定项数、且第 i 个镜头用的就是已绑定项里的第 i 项**，模型排错顺序会被拒绝并只修一次。这条保证是**相对顺序压紧**，不是固定槽位：已绑定项按清单编号从前往后成镜，跳过的项不留空镜头，后面的素材往前顶（跳过第 1、2 项时，第 3 项的素材会成为第 1 镜）。此前文档与向导页脚都写成「第 3 项 → 第 3 镜」，这在跳过前面的项时不成立，已按校验器实际行为改正，契约测试也从锁死错误承诺改为锁死这两句。跳过项的秒数由剩下的镜头吸收（总长在建项目时已定），向导会在跳过时说出来。清单读不到或某一项已不在清单里时**不生成计划**，避免绑定关系静默失效、退回成模型自选顺序；同理，清单已绑定过素材时拒绝重新生成清单，否则已拍素材会被重新解释成另一项——读不到那个项目时按 `STORAGE_READ_FAILED` 可重试地拒绝，不把一次瞬时读盘失败当成「项目已删除」的许可。

  复刻服务的写入也按 `taskId` 串起来了：`run` / `startProject` / 落盘共用一条队列，`startProject` 建完项目后**重新读盘**再写链接，遇到清单已被重新生成或已链到别的项目时删掉刚建的空项目并说明原因，而不是把新清单盖回旧文档、留下孤儿项目。向导的失败重试改为「重做失败的那一步」：此前无论哪一步失败，重试都按当前阶段猜（有项目就去生成计划），素材不够时点重试会跑去规划。

  仍然没有解决的：清单只说该拍什么，界面明确写出「不代表画面里真的有这些内容」——系统没有看过用户拍的素材，无法核对绑定的文件是否真是那一项要的画面——[#112](https://github.com/AIMFllyYS/HongTai-AI-Agent/issues/112) 之后规划器能看到画面里有什么，但**没有做「清单要的」与「画面有的」比对**，绑错文件仍然不会被拦下。脚本草稿只是参考，最终口播由规划器按绑定后的素材重写。向导只到「生成脚本与字幕」为止，随后跳转微调页，成片仍要回制作页合成；浏览器运行时本就不能合成。当前证据是 12 条服务端集成单测（含乱序绑定、顺序拒绝、清单丢失、重生成保护、读盘失败 fail-closed、过期待绑定标记）与 18 条 Web 单测/契约测试，**没有真机验证**，逐项调用系统选择器与 WebView 重建后的绑定保持只有单测证据。「本地合成至少 3 个画面」这个门槛也收进了 `packages/core` 的生产边界常量，向导、合成服务和清单可用性判定不再各写一个 3。

  [#112](https://github.com/AIMFllyYS/HongTai-AI-Agent/issues/112) 第一半（AI 侧）落地：`packages/ai` 新增 `asset-insight.v1` 与 `AssetInsightFlow`，把一个已导入素材的画面帧交给视觉模型，只取回「看得见什么」——画面描述、出镜主体（与蓝图共用同一份封闭词表，便于日后比对「清单要的」和「画面有的」）、几个单词标签，以及这份素材是否根本没法用与该重拍什么。这一条**故意不给模型看需求清单、文件名或经营需求**：告诉它我们希望看到什么，描述就会变成附和，而这份文档只有在能和计划不一致时才值得存在。

  同样故意的是**没有修复轮**：仓库里其他 Flow 失败后会再要一次，但修复调用是纯文本的，看不到图的模型只能把描述编出来。这里一次调用不通过就如实失败，由调用方把这个素材留成「没看过」。描述还会过一遍既有的医疗越界正则（确诊/概率数值/用药剂量/健康评分一律拒绝），素材审阅不是诊察。

  「到底看过没有」现在是**计划里的数据，不是文案**：`production-plan.v3` 增加可选的 `grounding`（`asset_insight` / `blind` / `not_applicable` 加上被识别的素材 id），由运行过程推导而**不问模型**（能自己声明就会选好看的那个值），`validateProductionPlan` 硬校验它自洽、id 真实且不重复。数字人模式记 `not_applicable`（口播是用户自己的稿子配自己的录像，没有素材要匹配），微调页改文案不会让计划变成「看过」或「没看过」。字段可选是为了让 #107 到 #111 期间已经存在的 v3 计划仍然打得开——那些运行确实完全没有视觉，读成 `blind` 是事实。

  第二半（原生侧与串联）随后落地：Kotlin 新增 `ProductionInsightFramePolicy`（纯 JVM 可测的取帧位置与上限：最多 3 帧、长边 2048、JPEG q90、单帧 15 MiB 硬顶）与 `ProductionInsightFrames`（图片走既有的私有观察图规范化器，视频用 `MediaMetadataRetriever` 按策略取帧），派生图只写进项目私有的 insight 目录并在重取时先清旧文件；`insightFrames` 作为新的插件方法在 `PRODUCTION_EXECUTOR` 上跑，不占主线程。`standalone-production-service` 在生成计划前**逐个**素材抽帧并调用 `AssetInsightFlow`，结果落进 `project.json` 的素材记录，下次规划直接复用，不会重复花视觉调用。

  这条链路上每一步失败都退回「没看过」而不是拦住成片：旧 APK 或浏览器里没有这个插件方法、抽不出帧、视觉能力没配好、模型返回坏 JSON、模型自己说画面没法用——五种情况都只让该素材保持未识别，计划照常生成并如实记 `blind`。其中**第五种不能说成「没看过」**：模型看过并给出重拍建议（例如「太暗了，建议开灯后重拍」）时，那条建议会作为 `ProductionAsset.reshootAdvice` 上到素材卡与微调页，微调页改说「系统看过你上传的画面，但有 N 个素材看不清」，并提示重拍比改文字更有用。判定不可用的结果会被缓存、重新生成不再重复调用视觉——这是有意的：同一张全黑照片再看一次只会得到同一句话，用户需要的是换素材。写出的派生帧还会验 JPEG 头，截断或半写的文件按未识别处理，不让模型去描述噪声再报成「已识别」。送进规划提示词的素材字段现在**逐项投影**而不是整条铺开：私有文件路径、落盘字节数和「该不该重拍」的判断都不再进提示词（此前整条铺开会把私有路径送给云端模型，本次一并收掉），标成不可用的素材也不贡献描述——「看过但什么也没看清」不是 grounding。

  `asset_insight` 的准确含义是**这个素材的画面帧确实被送去看过一次**，仅此而已：它不保证那份描述与画面相符（模型仍可能看错），也不保证旁白只讲了描述里提到的东西——「不得补充 insight 没提到的内容」只是提示词规则，没有机器校验，这与 [#110](https://github.com/AIMFllyYS/HongTai-AI-Agent/issues/110) 的「提示词说了不能编 ≠ 内容不是编的」是同一类边界。同样**没有做**的是「清单要的」与「画面有的」比对：绑错文件不会被拦下。

  微调页会把这件事说出来：盲配时明说「系统没有看过你上传的画面，文字不一定对得上每个镜头」，识别过时说清**是几个**素材被识别过、剩下的仍按拆解结构写；读取端把缺失或未知的 `grounding` 一律读成 `blind`，宁可少承诺。当前证据：8 条 `asset-insight` 单测 + 3 条规划侧单测 + 1 条 v3 校验单测 + 4 条服务端串联单测（含五种退化原因、复用缓存、私有路径不外泄）+ 3 条读取端单测 + 1 条页面契约测试 + 4 条 Kotlin 取帧策略单测。**没有真机验证**：真实图片与视频是否真能抽帧、派生图是否真被视觉通道接受，只有等 APK 上机才算数。

  代码审查后又做了三处收敛：字幕条数只由文案与模板行盒决定，**不再按镜头时长合并字幕**（原合并逻辑经穷举验证在任何中文旁白上都无法成功，已删除），镜头时长不够时如实产出偏短字幕，交由导出微调页提示用户加长镜头；贪心切分留下的两三字碎片字幕改为并入前一条或前移切点；字数与强调词上限改由 `packages/core` 单一来源提供给 Zod Schema，两种模式的 v3 组装也合并为同一个 `withSubtitleTimeline`，避免同一处修复要改两遍。

  [#113](https://github.com/AIMFllyYS/HongTai-AI-Agent/issues/113) 随包装了 7 个原创几何贴纸（箭头、星标、对勾、角标 1、闪光、划线、气泡），清单在 `packages/core`，PNG 在 `apps/web/public/decorations/`。规划器只让模型选镜头、清单 id 和锚点；`startMs`/`endMs` 由 TypeScript 按该镜字幕推导，不让模型填时间轴。微调按新字幕重算窗口，不再把装饰写成空数组。Android 从 Capacitor 同步后的 `public/decorations/{id}.png` 读图，解析时文件不存在就失败，不会导出一条静默没有贴纸的成片。缺图或解不开会映射为 `PRODUCTION_DECORATION_MISSING`（`action: none`），界面说要重新安装完整应用，而不是「这次微调不能这样保存」。Web 预览与烧录共用 `decorationPreviewBox` 的宽度，不再另盖 50% 上限。当前证据是 TypeScript 与 JVM 单测；**没有真机 Media3 成片证据**。`allowedDecorationIds` 已由 `StandaloneProductionService` 在生成与微调两处传入随包清单，服务端测试夹具带着一个真实贴纸——去掉这行接线，计划会直接被判无效，所以这条链路不会静默变成「有清单但永远禁用」。没有装饰×字幕的像素碰撞校验，不能声称贴纸不挡字；也没有验证过 7 张 PNG 在真机上是否真被 Media3 叠出来。`floating_text` 渲染器仍在，本条没有它的生产者。数字人模式不选装饰。

  [#114](https://github.com/AIMFllyYS/HongTai-AI-Agent/issues/114) 把制作首页收成两个入口：Agent 模式与爆款复刻。数字人口播留在 Agent 流程里，不是第三张顶层卡；`ProductionMode` 服务契约仍是 `"montage" | "avatar"`。Agent 文案先说这台安装不一定能看画面，不写「看懂 / 理解素材」，也不把创建项目说成「一键制作视频」。已有未导出项目时工作台提供「再做一条 / 换一种做法」回到两张卡。离开 Agent 会清掉失败，避免选择屏上的重试重建刚放弃的项目。爆款复刻从制作页选一条成功拆解后进入既有 `/replica/:taskId`；没有拆解时说明先去采集并运行 AI 自动拆解。项目卡片、历史和导出微调页仍共用。证据是源码级契约测试，**没有浏览器截图或真机验证**。

## 最小验证基线

每次变更按影响范围选择验证，详情见[任务执行模板](任务执行模板.md)：

- TypeScript：`pnpm check` 与定向测试；
- Web：`pnpm --filter @hongtai/web build`，视觉改动补桌面与约 390px 截图；
- Android：相关 Gradle 单测、lint、构建；外部媒体、网络和 Media3 改动补真机证据；
- Release：签名、递增版本号、APK SHA-256 和不带降级参数的升级测试。

不要把“构建成功”“模拟器通过”或“某一个 AI 探测成功”表述为正式 release、物理真机或全部模型能力均已验证。
