## 1. 用户真正要解决的问题

用户最初把问题描述为“AI 应该流式输出模块 JSON，页面应随着标签值生成而更新”，经过真实代码分析后，本质被收敛为两个互相关联但不同的问题：

1. **传输流不等于业务进度。** Provider 已能接收 SSE/UTF-8 `content_delta`；页面缺少的是“某个业务模块已经闭合、通过 Zod 与语义校验，可以安全展示”的事件。页面不应渲染半截 JSON。
2. **一次性大 JSON 把用户反馈拖到最后。** 舌诊/面诊与内容拆解原本都是一次模型调用，等完整 JSON 校验、必要修复并保存后才有结果，用户中间只能看到转圈。
3. **旧修复停在字符串猜测层。** `StructuredStreamPreview` 用正则从未完成 JSON 中猜字段和字符数，无法可靠处理嵌套、转义、中文多字节和跨 chunk 字段，也不能证明内容符合 Schema。
4. **必须手动刷新有一个独立根因。** 旧 Pipeline/Runtime 的部分路径先通知 UI，后写 `events.jsonl` 或终态 `task.json`。页面收到通知立即重读时仍得到旧 `running`，而后续落盘没有第二次通知，所以只能靠手动刷新。

最终目标不是做 Agent，而是做两条简单、固定、可测试的五模块 AI 调用流程，并把已校验模块作为运行期安全投影发给 UI：

```text
OpenAI 兼容 Provider SSE
  -> packages/ai 固定五模块 Flow
  -> 模块 Zod + 语义校验
  -> AppRuntime v2 语义事件
  -> UI 流光等待 / 已校验模块渐显
  -> 五模块全部完成后组装最终文档
  -> 最终 Schema 校验
  -> 原子保存正式结果
  -> 持久化完成后才通知 completed/failed
```

## 2. 已批准、不可随意改写的架构决策

### 2.1 分层边界

- `packages/ai`：Prompt、模块 Schema、模块顺序、修复策略、Flow、安全规则。
- `packages/core`：版本化 DTO、任务/报告公共契约、先持久化后通知规则。
- `packages/capacitor-runtime`：组合共享 Flow、私有存储、按 ID 订阅、single-flight、Android I/O 端口。
- `apps/web`：只通过 `AppRuntime` 和稳定 DTO 展示，不解析供应商原始流。
- `android/app`：不新增 Prompt、Schema、业务状态机或 UI 文案。
- `packages/platforms`：本任务不改。
- `apps/cli`：继续作为共享 Flow 的开发回归入口，不成为 APK 运行依赖。

### 2.2 舌诊/面诊固定五模块

顺序和 ID 不允许动态变化：

1. `visual-observations`：唯一携带私有图片的视觉调用；输出 `imageQuality`、`observations`。
2. `observation-summary`：只使用模块 1 的已校验文本结果；输出 `summary`。
3. `wellness-recommendations`：输出 `wellnessReferences`、`recommendations`。
4. `safety-limitations`：输出 `safetyGuidance`、`limitations`、`disclaimer`。
5. `follow-up-questions`：输出 `followUpQuestions`。

固定约束：

- 新报告 `promptVersion = diagnosis-modular.v1`。
- 正式文档仍为 `diagnosis-report.v1`；旧 `diagnosis-initial.v1` 报告继续可读。
- `schemaVersion`、用户选择的 `mode`、`promptVersion` 由本地逻辑写入，不让模型猜。
- 只有模块 1 的权限失败映射为 `AI_VISION_UNAVAILABLE`；文本模块权限失败保留 `AI_PERMISSION_DENIED`。
- 图片不可用时 `observations` 必须为空，后续只能生成重拍、限制、安全提醒和必要追问，不能凭空生成健康参考。
- 任一模块失败立即停止，后续模块保持 `pending`。

### 2.3 内容拆解固定五模块

1. `overview`：输出 `overview`。
2. `hook-drivers`：输出 `hook`、`painPoints`、`emotionalDrivers`。
3. `structure-claims`：输出 `structure`、`coreClaims`。
4. `style-template`：输出 `style`、`reusableTemplate`。
5. `risks-boundaries`：输出 `risks`。

固定约束：

- `source.taskId/platform/contentType/sourceKind` 只由本地真实任务写入。
- 每个带 `evidenceRefs` 的模块在发送 UI 事件前校验引用确实存在。
- 证据不足时允许空数组和明确说明，不允许补写标题、作者或外部常识作为内容证据。
- 正式文档仍为 `content-analysis.v1`，不新建 v2 迁移。

### 2.4 Prompt 与修复策略

- 这是提示词精调，不建设训练数据集、Fine-tuning 平台、模型注册或部署系统。
- 每个领域一个公共规则文件，五个真实模块各一个 Prompt 文件。
- 每个模块最多一次格式/语义修复；没有动态 Agent 循环。
- 正常路径五次模型调用，理论上最多十次；Provider 网络重试仍沿用既有 0/1s/3s 策略。
- Provider 原始流只留给 CLI/私有运行审计；页面事件只含已校验模块。
- 不持久化模块半成品；WebView/进程退出后不恢复模块中间结果，重试从模块 1 开始。

## 6. 刚发现但尚未实现的最后一个阶段 4 边缘竞态

中断前准备处理的问题是：

- `TaskHomePage.loadHistory()` 可能在订阅事件之后才返回旧列表，从而用旧 `list()` 结果覆盖刚刚通过 `subscribeChanges()` 合并的新状态。
- `ObservationStartPage.loadSessions()` 与 running session 的终态订阅也存在同类极短窗口。
- 核心层“先持久化、后通知”已经正确；这里是页面初次异步读取与内存事件合并的竞态，不能靠轮询解决。

最小修复方向：

1. 先补失败测试，证明“列表读取开始后收到 upsert/delete/终态事件，列表稍后返回旧值”不会回退页面。
2. 保持现有 `applyTaskHistoryChange()` 和 `upsertObservationSession()` 纯函数。
3. 为每次列表读取记录开始时的本地事件游标；列表返回后，依次重放读取期间收到的窄变更事件，再提交合并结果。
4. 同时用一个很小的请求序号阻止更早的读取晚于更新读取覆盖结果。
5. 不引入 Redux、状态机框架、轮询、数据库或通用事件总线。
6. 删除事件必须作为事件重放，不能只按 `updatedAt` 合并，否则旧列表会把已删除任务复活。

这项修复尚未写入工作区。不要把“24/24 通过”误读成这个竞态已经有测试。
