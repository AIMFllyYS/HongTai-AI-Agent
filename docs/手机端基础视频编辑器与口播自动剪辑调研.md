# 手机端基础视频编辑器与口播自动剪辑调研

> 调研日期：2026-08-11。本文是产品与技术选型研究，不表示下列新能力已经实现。当前真实能力仍以[当前能力与发布状态](当前能力与发布状态.md)为准。

## 1. 结论先行

宏泰 AI 已经具备一条真实但很窄的本地成片链路：

```text
公开作品采集
→ content-analysis.v1
→ 用户导入 3–12 份本机素材
→ AI 生成 production-plan.v1
→ Android 系统 TTS
→ Media3 合成固定 9:16 MP4
```

这条链路能自动生成视频，但还不是类似剪映的基础编辑器，也不是“真人口播原片自动精剪”。当前不能在时间线上修剪、分割、重排、修改字幕、恢复误删片段、预览最终 Composition 或撤销操作。

推荐方向不是引入一个完整第三方编辑器，也不是改成 FFmpeg 命令系统，而是：

1. 保留 Jetpack Media3 作为 Android 唯一预览/导出媒体内核；
2. 在共享 TypeScript 本地应用逻辑层增加一个非破坏性的 `edit-project.v1`；
3. 让当前 `production-plan.v1` 和未来真人口播分析都编译到同一种编辑工程；
4. 先做口播最需要的剪切、字幕、重排、音量、画幅和撤销，再做有限转场；
5. AI 只生成带理由和置信度的“建议编辑”，用户确认后才改变编辑工程。

一句话定位：**不是在手机里复刻完整剪映，而是做一台以口播自动精剪为主、人工修正成本很低的专用剪辑机。**

## 2. 当前项目真实能力

### 2.1 已有用户能力

| 能力 | 当前事实 | 与自动剪辑的关系 |
| --- | --- | --- |
| 公开链接采集 | 抖音、小红书、B站与实验性快手的单条公开内容进入七阶段任务 | 提供参考作品、媒体与文稿证据 |
| 内容拆解 | 基于真实转写 segment 或图文 paragraph 生成 `content-analysis.v1` | 可提取结构、卖点和叙事顺序 |
| OpenAI 兼容连接 | 文本、视觉、ASR 独立配置和探测 | 可继续承担口播转写与编辑建议 |
| 本地素材导入 | 系统选择器导入图片、MP4、MP3/M4A/WAV，并复制进项目私有目录 | 已有编辑素材入口，但没有素材管理操作 |
| 制作规划 | 依据正式拆解、经营需求和素材生成 `production-plan.v1` | 已有 AI 镜头计划，但计划字段不足以表达编辑时间线 |
| 本地渲染 | Android TTS + Media3 Composition，输出 720×1280、30fps、H.264/AAC MP4 | 已有可靠的最小导出骨架 |
| 成片预览 | Web 页面播放已经导出的 MP4 | 只能看结果，不能实时预览编辑工程 |

### 2.2 当前渲染器实际支持

当前 `ProductionRenderer` 已经使用 Media3 1.10.1 完成：

- 图片和视频顺序拼接；
- 视频从 0 开始截取，不足时重复使用；
- `cover` / `contain` 画幅适配；
- 固定样式的文字字幕叠加；
- 每镜头 Android 系统 TTS；
- 旁白轨与循环背景音乐混音；
- H.264/AAC MP4 导出与进度回调；
- 临时文件成功后替换正式成片。

### 2.3 当前明确缺口

| 缺口 | 现状影响 |
| --- | --- |
| 没有源素材入点/出点 | 视频只能从 0 秒开始取，无法精确保留口播句子 |
| 没有时间线编辑模型 | AI 计划、UI 状态和原生 Composition 无法共享一个可编辑真相源 |
| 没有分割/删除/恢复/重排 | 用户无法修正 AI 的切点和镜头顺序 |
| 没有逐字或逐句时间锚 | 字幕只是每镜头一条静态文字，不能准确跟随真人口播 |
| 没有原声轨策略 | 当前视觉视频一律移除原声，更适合 TTS 成片，不适合真人口播 |
| 没有编辑预览 | 只能完整导出后看结果，试错成本高 |
| 没有撤销/重做和版本校验 | 不适合频繁编辑，也存在并发覆盖风险 |
| 没有删除素材与存储预算 | 大视频会持续占用应用私有空间 |
| 导出不可取消/恢复 | Transformer 虽支持取消，但当前桥接没有暴露；进程退出也不续跑 |
| 没有设备能力预检 | HDR、HEVC、旋转元数据和厂商 MediaCodec 差异仍需真机矩阵验证 |

因此，当前产品应被称为“自动制作器”，不能称为“基础视频编辑器”。

## 3. 必须区分的两条产品路径

### 3.1 模式 A：稿件驱动的自动成片

这是现有能力的延伸：参考作品拆解 + 用户素材 + AI 镜头计划 + TTS。它适合没有真人原片、希望快速生成宣传短视频的用户。

下一步价值主要来自可编辑性：用户能调整镜头顺序、字幕、素材裁剪、BGM 音量和封面，而不是每次重新让 AI 生成整份计划。

### 3.2 模式 B：真人口播原片自动精剪

这是项目核心目标需要补上的能力：用户导入一段照着明确稿件拍摄的长视频，系统自动找出可保留内容、停顿、重复、口误和重拍段，生成一版可复核的短视频。

建议的第一版输入：

- 1 个主口播视频；
- 可选的原始口播稿；
- 可选的图片/短视频补充素材；
- 目标画幅、时长和字幕样式。

建议的第一版输出：

- 保留区间和删除候选；
- 与保留区间绑定的句级字幕；
- 每个删除候选的原因和置信度；
- 一份可撤销、可手工修正、可再次导出的编辑工程；
- 最终 H.264/AAC MP4。

两种模式必须共用 `edit-project.v1` 和同一个 Media3 编译器。否则用户在模式 A 中修改的字幕/镜头能力无法复用到模式 B，后续维护会形成两套状态机和两套导出逻辑。

## 4. “类似剪映基础功能”的最小定义

不建议把贴纸商店、模板市场、复杂关键帧、美颜、抠像和几十种转场放进第一阶段。对口播视频，真正决定可用性的功能顺序如下。

### 4.1 P0：形成编辑器闭环

| 功能 | 最小交互 | 底层要求 |
| --- | --- | --- |
| 播放与定位 | 播放/暂停、拖动游标、跳到片段 | 可寻址预览与统一毫秒时间轴 |
| 缩略图时间线 | 显示主轨缩略图、当前时间和片段边界 | 异步抽帧、缓存和可见区域加载 |
| 修剪 | 拖动左右把手修改入点/出点 | `clipStartMs` / `clipEndMs` |
| 分割 | 在游标处分成两个片段 | 非破坏性复用同一个 assetId |
| 删除与恢复 | 删除片段；撤销可恢复 | 命令日志或有界 undo/redo |
| 重排 | 拖动片段改变顺序 | 稳定 clipId，不以数组下标作为身份 |
| 字幕编辑 | 修改文本、显示区间和基础样式 | 独立 caption cue，不烧进源素材 |
| 音量 | 原声、旁白、BGM 独立调节 | 轨道增益和峰值保护 |
| 画幅 | 固定 9:16，支持 fit/crop 和位置 | 与 Media3 Presentation/Crop 映射 |
| 导出 | 进度、取消、失败保留工程、成功原子替换 | single-flight Transformer 与稳定错误码 |

### 4.2 P1：口播效率能力

- 按静音候选一键删停顿，并允许调整阈值；
- 根据 ASR 与稿件对齐标记重复、回读、明显口误和遗漏；
- 自动生成句级字幕，支持安全区、字号、颜色和每行字数；
- 删除后自动保留 120–200ms 呼吸边界，避免机械掐字；
- 过短切点合并、最短镜头保护和连续跳切提示；
- BGM 自动压低，但第一版不做复杂侧链压缩器；
- 自动建议 9:16 主体位置，用户可手动调整。

### 4.3 P2：有限增强

- 图片/视频 B-roll 覆盖轨；
- 简单淡入淡出和黑场，不做转场市场；
- 贴纸/水印/标题卡；
- 变速与局部静音；
- 低清代理预览和后台可恢复导出。

### 4.4 暂不做

- 多人协作、云工程和账号同步；
- 多层自由关键帧动画；
- 美颜、磨皮、身体重塑和实时抠像；
- 曲线变速、光流补帧和复杂音频工作站；
- 模板/贴纸/音乐市场；
- 自动发布到内容平台；
- 逐帧去水印。

## 5. 推荐的编辑工程模型

`production-plan.v1` 应继续表示 AI 的制作意图，不应直接扩成万能时间线。建议把它编译为独立的 `edit-project.v1`：

```text
production-plan.v1 ─┐
                    ├→ EditProjectCompiler → edit-project.v1
口播分析结果 ────────┘                         │
                                               ├→ 预览适配器
用户编辑命令 ─→ EditProjectReducer ────────────┤
                                               └→ Media3 Composition 编译器 → MP4
```

建议字段：

```ts
interface EditProjectV1 {
  schemaVersion: "edit-project.v1";
  projectId: string;
  revision: number;
  output: { width: 720; height: 1280; fps: 30 };
  assets: Array<{
    assetId: string;
    kind: "video" | "image" | "audio";
    durationMs?: number;
    displayName: string;
  }>;
  videoTrack: Array<{
    clipId: string;
    assetId: string;
    sourceStartMs: number;
    sourceEndMs: number;
    timelineStartMs: number;
    fit: "cover" | "contain";
    volume: number;
  }>;
  captions: Array<{
    cueId: string;
    startMs: number;
    endMs: number;
    text: string;
    styleId: string;
  }>;
  audioTracks: Array<{
    trackId: string;
    role: "original" | "narration" | "music";
    assetId: string;
    timelineStartMs: number;
    sourceStartMs: number;
    sourceEndMs: number;
    gain: number;
  }>;
}
```

关键约束：

- 时间使用整数毫秒，不使用浮点秒；
- `assetId`、`clipId`、`cueId` 永久稳定；
- 素材永不因时间线删除而被立即物理删除；
- 每次写入携带 `revision`，拒绝旧版本覆盖；
- 同一 `projectId` 的分析、编辑和导出串行化；
- 编辑操作采用明确命令，例如 `splitClip`、`trimClip`、`moveClip`、`updateCaption`；
- AI 建议先保存为 suggestion，不直接写正式轨道；
- 项目 JSON 与命令日志先写临时文件再替换，失败保留上一成功版本。

这仍符合现有分层：`core` 定义工程和命令，`ai` 生成建议，`capacitor-runtime` 组合流程，Kotlin 只把已验证工程编译成 Media3 对象并执行 I/O。

## 6. 真人口播自动精剪算法

### 6.1 第一版不应让大模型直接输出最终切点

精确切点需要音频时间证据。大模型擅长判断语义重复和稿件覆盖，不擅长凭一段文字可靠地产生毫秒级边界。因此采用“确定性信号先切候选，AI 再解释和排序”的两阶段流程。

### 6.2 推荐流程

1. **媒体规范化**：探测旋转、时长、音轨、HDR、分辨率和编码器能力；不立即转码源文件。
2. **音频分析**：解码为 16kHz 单声道 PCM，计算短窗能量；第一版可以不引入 ML VAD。
3. **ASR**：复用用户配置的 OpenAI 兼容 ASR，要求 segment 时间戳；若供应商提供可信 word 时间戳则保留。
4. **稿件对齐**：对明确口播稿做规范化后，按句进行动态规划/编辑距离对齐；保留“未说、重复说、改说”的证据。
5. **候选切点**：长静音、重复句、重新起句、明确口头填充词形成候选；每个候选包含来源时间、理由和置信度。
6. **边界修正**：优先落在静音中心，保留 120–200ms 句前/句后余量；禁止切进高能量语音中心。
7. **节奏约束**：拒绝过短保留段，合并间隔过小的删除区间，提示过密跳切。
8. **字幕生成**：从最终保留区间重新映射时间，不直接复用删除前的绝对时间；按语义和阅读速度分行。
9. **人工复核**：时间线上用不同颜色显示“建议删除、已接受、已保留”，支持逐项试听。
10. **确定性导出**：只有用户接受的命令进入 `edit-project.v1`，Media3 再生成 Composition。

### 6.3 证据优先级

```text
音频静音/VAD 边界
> ASR segment/word 时间戳
> 原稿与转写对齐结果
> 大模型语义判断
```

任何低置信度口误或重复都只提示，不自动删除。对中文口播，“嗯、啊、然后、就是说”有时承担语气和连接作用，不能仅按词表全删。

### 6.4 本地模型的时机

第一版继续复用现有 OpenAI 兼容 ASR，避免立即把大型模型塞进 APK。以后需要完全离线时再做独立实验：

- `whisper.cpp`：MIT，有 Android 示例和实验性 word 时间戳；优点是生态成熟，风险是模型体积、耗时、发热和时间戳精度；
- `sherpa-onnx`：Apache-2.0，覆盖 Android、Kotlin、ASR、VAD 和标点；能力广，但模型选择、包体和中文时间戳必须单独基准测试；
- Silero VAD：MIT，小型 ONNX VAD，适合作为能量检测不够稳时的第二阶段，而不是第一版前置依赖。

模型许可证不等于模型权重、训练数据和分发条款自动相同，正式内置前必须逐模型复核。

## 7. Android 媒体技术选型

### 7.1 主方案：继续使用 Jetpack Media3

官方 Media3 Transformer 已支持裁剪、缩放、旋转、Crop、文字/图片 Overlay、音频处理、多个素材的 Composition 和 MP4 导出；Media3 1.9 起提供实验性的 `CompositionPlayer`，可用同一个 Composition 预览多素材编辑。项目当前已经锁定 1.10.1，复用成本最低。

建议职责：

- `Transformer`：最终导出、进度、取消和稳定错误分类；
- `Composition` / `EditedMediaItemSequence`：主视频轨、原声/旁白/BGM 轨；
- `MediaItem.ClippingConfiguration`：片段入点/出点；
- `Effects`：画幅、裁剪、旋转、文字/图片覆盖和音频增益；
- `CompositionPlayer`：先在受控实验中验证真实预览，不能因实验 API 直接绑定业务 DTO；
- ExoPlayer/HTML video：在 CompositionPlayer 证明稳定前承担单片段预览或代理预览。

官方当前明确说明 Composition 不支持音视频 crossfade。第一版使用硬切；淡入淡出可在验证后以受控效果实现，不能承诺完整转场系统。

### 7.2 WebView 与原生预览的边界

时间线、字幕编辑、按钮和状态继续属于 React UI。Kotlin 不决定编辑逻辑或中文文案。

预览建议分两步：

1. MVP 用 HTML video + CSS 字幕/画幅做快速代理预览，并提供低清草稿导出来确认最终效果；
2. 另做 CompositionPlayer 原生预览 spike。若要在 Capacitor 中承载原生 Surface，只暴露 `preview(editProject)`、`seek(ms)`、`play/pause` 和事件，不把时间线业务搬到 Kotlin。

必须承认代理预览与最终 Media3 输出可能有字体、裁剪和时序差异；未通过像素/时间对照前不能声称所见即所得。

## 8. 开源项目对照

| 项目 | 许可证/状态 | 可借鉴 | 对宏泰 AI 的结论 |
| --- | --- | --- | --- |
| [AndroidX Media3](https://github.com/androidx/media) | Apache-2.0，Google 持续维护 | Transformer、Composition、效果、官方 demo、CompositionPlayer | **主依赖，继续使用** |
| [android-video-trimmer](https://github.com/a914-gowtham/Android-video-trimmer) | MIT；1.8.0 起改用 Media3，2026-01 有 beta release | 双把手修剪、缩略图条、Activity 交互 | **只参考 UI/交互**；不引入其独立 Activity 和工程模型 |
| [LiTr](https://github.com/linkedin/LiTr) | BSD-2-Clause | 硬件转码、trim、滤镜、watermark、filmstrip、取消和统计 | **备用实现/源码参考**；与 Media3 能力重叠，不并列引入第二内核 |
| [DeepMedia Transcoder](https://github.com/deepmedia/Transcoder) | Apache-2.0 | 裁剪、拼接、变速、缩略图、音频策略 | **备用参考**；同样会形成第二套编解码管线 |
| [Mp4Composer-android](https://github.com/MasayukiSuda/Mp4Composer-android) | MIT | OpenGL 滤镜、crop、trim、rotate | **历史参考**；JitPack 和较老 API，不作为新基座 |
| [FFmpegKit](https://github.com/arthenica/ffmpeg-kit) | 默认 LGPL-3.0，启用部分库后 GPL-3.0；原仓库已退役 | FFmpeg 完整滤镜和格式生态 | **不作为主方案**；许可证、包体、ABI、供应链和维护成本过高 |
| [Auto-Editor](https://github.com/WyattBlue/auto-editor) | Unlicense；CLI，Nim/Python | 音量/运动分析、静音 margin、可解释自动切段、导出编辑时间线 | **算法和交互参考**；不能直接进入 APK |
| [whisper.cpp](https://github.com/ggml-org/whisper.cpp) | MIT | 离线 ASR、Android 示例、时间戳 | **离线 ASR 候选**；先做设备基准，不立即内置 |
| [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) | Apache-2.0 | Android/Kotlin ASR、VAD、标点及多架构支持 | **离线语音平台候选**；模型级复核后再选 |
| [Silero VAD](https://github.com/snakers4/silero-vad) | MIT | 小型 ONNX 语音活动检测 | **可选增强**；能量算法不够稳时再引入 |
| [WhisperX](https://github.com/m-bain/whisperX) | BSD-2-Clause；桌面 Python | 强制对齐与 word 时间戳的思路 | **研究参考**；移动端依赖重，且近期有时间戳回归案例 |

没有找到一个许可证清晰、维护活跃、可直接嵌入 Capacitor Android、同时提供成熟时间线 UI、准确预览和可控导出的“开源剪映”。成熟项目通常只解决修剪或转码；完整编辑器要么是桌面软件，要么是商业 SDK，要么许可证/移动端架构不适合。因此应组合官方 Media3 与自有最小编辑工程，而不是寻找一个万能仓库。

## 9. 分阶段实施路线

### 阶段 0：技术 spike，不接正式 UI

- 用 Media3 1.10.1 验证任意 `sourceStartMs/sourceEndMs` 的多段拼接、原声保留、字幕重映射和 BGM；
- 验证 Transformer 取消、重复导出、HDR→SDR 和异常后资源释放；
- 在至少一台低端、一台主流和一台较新物理 Android 设备测试 3、10、30 分钟素材；
- 单独验证 CompositionPlayer 在 Capacitor 容器中的 Surface、seek、字幕和音频同步；
- 输出基准：导出倍率、峰值内存、温升、失败码、旋转/HDR/可变帧率兼容。

停止条件：若 CompositionPlayer 无法在现有 React/Capacitor 结构中稳定嵌入，MVP 明确采用代理预览 + 草稿渲染，不阻塞编辑工程。

### 阶段 1：`edit-project.v1` 与无 UI 编辑内核

- 在 `packages/core` 定义工程、命令、revision 和校验；
- 把 `production-plan.v1` 编译成编辑工程；
- 实现 trim/split/delete/move/updateCaption/setGain 的纯 TypeScript reducer；
- 同一项目写入 single-flight，原子保存 snapshot + command log；
- Kotlin 新增严格解析器，只执行已验证工程。

验收：相同输入和命令得到相同项目 JSON；撤销/重做不改变素材；并发旧 revision 被拒绝；导出时长与轨道计算一致。

### 阶段 2：最小手机时间线

- 播放器、游标、可见范围缩略图、单视频主轨；
- 修剪、分割、删除、重排、撤销/重做；
- 句级字幕编辑、原声/BGM 音量；
- 导出、取消、失败重试和空间不足提示；
- 390px 宽度下完成触控和可访问性验收。

验收：用户无需重新调用 AI，就能修正自动方案并得到新成片。

### 阶段 3：口播自动精剪 MVP

- 导入单个真人口播视频与可选稿件；
- 音频能量/静音分析 + 现有 ASR segment；
- 稿件句级对齐、重复/重拍候选、删除 margin；
- 建议逐项接受、全部接受和恢复；
- 最终字幕按删除后的时间线重映射。

验收数据不能只用一个演示视频。至少包含安静/嘈杂、快/慢语速、有/无稿、普通话/口音、横/竖屏、长静音和多次重拍样本，并人工标注基准切点。

### 阶段 4：准确预览与有限 B-roll

- CompositionPlayer 若 spike 通过，则替换代理预览适配器；
- 增加一个覆盖轨，支持图片/短视频 B-roll；
- 自动建议覆盖区间，但不自动替换主口播音频；
- 增加标题、图片水印和简单淡入淡出。

### 阶段 5：离线与性能增强

- 依据真实用户对离线的需求，再比较 whisper.cpp 与 sherpa-onnx；
- 按设备能力下载模型，不把所有模型打进基础 APK；
- 增加低清代理、缩略图缓存淘汰、存储预算和可恢复导出；
- 建立设备编码器黑名单/降级策略，但不得放宽 TLS 或伪造成功。

## 10. 关键验收指标

### 10.1 编辑正确性

- 所有切点误差以帧或毫秒记录；30fps 下视觉切点目标误差不超过 1 帧；
- 删除区间后字幕不得跨越删除边界或出现负时长；
- 预览时间和导出时间在片段边界处可解释一致；
- 相同工程重复导出，轨道、时长和字幕内容一致；
- 撤销/重做 50 次后工程校验仍通过。

### 10.2 自动精剪质量

- 自动删除的高置信度区间中，不得系统性切掉有效字音；
- 分别报告“建议准确率”和“用户接受率”，不能只报告节省了多少时长；
- 原稿缺句、即兴发挥和同义改写必须保留可解释证据；
- 低置信度只提示，不能默认删除；
- 对 5–10 分钟常见口播，人工复核时间应显著低于从零剪辑。

### 10.3 Android 运行质量

- 真机验证 H.264 编解码、旋转、可变帧率、HDR/SDR、长素材、低空间和进程中断；
- 峰值存储同时计算源素材、代理、TTS/PCM、临时输出和正式输出；
- 取消后及时释放 codec、Surface、TTS 和临时文件；
- 导出失败不覆盖旧成片，不删除用户素材；
- UI 不读取私有路径、MediaCodec 异常全文或原始 AI 响应。

## 11. 最终建议

优先级应当是：

```text
可编辑工程
→ 基础时间线
→ 真人口播自动切点
→ 准确预览
→ B-roll 与有限效果
→ 离线模型和高级能力
```

不建议先做滤镜、转场和模板市场。它们看起来像剪映，但不会解决项目的核心价值。宏泰 AI 最强的差异化应当是：用户给出明确口播稿和一段原片，系统能在手机本地或用户选择的兼容 AI 服务帮助下，快速给出一版有证据、可恢复、可手工微调的精剪结果。
