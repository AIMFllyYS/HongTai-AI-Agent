# 后台持续运行机制（TaskGuard）规划

> 状态：**源码已实施（2026-08-31），随 `v0.1.28`/code36 发布；真机验收待用户执行**。用户决策（2026-08-30）：①实现方式采用 `@capawesome-team/capacitor-android-foreground-service` 插件 + 最小自写 Kotlin 补件；②后台运行开关默认开启；③覆盖全部长任务。

**中断语义结论（实施时源码核查）**：「进入后台 → TASK_INTERRUPTED」的实际路径只有两条——①冷启动 `recoverInterruptedWork()`（进程真实重建，保留为正确兜底）；②运行期读到「无活跃 mutation 的 planning/rendering」（链路失联）。四类长任务的 mutation 与 TaskGuard 护持经同一个 `#track`/`track` 包装同生命周期绑定：任务真在运行时 mutation 必然活跃，后台返回不会误判中断；FGS+WakeLock 把进程冻结/被杀概率大幅压低。因此无需修改 `runtime-interruption.ts` 的语义本身。

**setTimeout 审计结论**：生产代码唯一使用点是 `openai-compatible-retry.ts` 的重试退避（`[0, 1s, 3s]`）。后台节流会把等待拉长（普通 ≥1s、深度节流最长约 1 分钟）但回调仍触发，任务不停滞；退避窗口占任务生命周期比例极小，改造为事件驱动收益不抵成本，如实记录不改。测试文件中的 setTimeout 不在管线路径。

## 一、问题定义

**用户可感知的现状**：只要熄屏或离开 App（切后台），正在运行的采集、拆解、观察、制作管线立即停止；返回后任务被标记中断，需要手动重试。

**用户期望**：像正常原生 Android 应用一样，熄屏/切后台后长任务继续运行；设置页提供开关（后台运行、电池优化引导等）。

## 二、根因分析（当前为什么会停）

经源码核查与外部调研，停止运行由四层机制叠加造成，缺一不可破：

| # | 机制 | 现状 | 后果 |
| --- | --- | --- | --- |
| 1 | **进程冻结（cached app freezer）** Android 12+ 默认开启 | App 无任何前台组件，退后台约 10 分钟（AOSP 默认；部分国产 ROM 60–150 秒）降为 cached 后被 cgroup 冻结 | 进程保活在 RAM 但 CPU 完全暂停，JS 编排链、原生请求全部停摆 |
| 2 | **Doze 低电耗模式** | 熄屏 + 未充电即进入 Light Doze；熄屏 + 静置约 30 分钟进入 Deep Doze | Light Doze 限制网络与计算；Deep Doze **忽略一切应用的 WakeLock 并断网**（前台服务也不豁免，仅电池优化白名单部分豁免） |
| 3 | **WebView JS 节流** | 页面不可见后 Chromium 对 `setTimeout/setInterval` 递增节流 | 本项目 `runAutomaticPipeline`（`standalone-production-service.ts`）是顺序 `await` 事件驱动、非定时器轮询，此层风险较低，但进程冻结/被杀仍会中断链路 |
| 4 | **无前台服务（FGS）** | Manifest 仅 `INTERNET`、`ACCESS_NETWORK_STATE`、`WAKE_LOCK`；唯一保活手段是 `ActiveWorkScreenStay` 的 `FLAG_KEEP_SCREEN_ON`（仅任务期间保持亮屏） | 熄屏即失效；进程无豁免冻结与后台回收的资格 |

另有一处**当前设计使然**：`runtime-interruption.ts` 把「进入后台」明确定义为中断（`TASK_INTERRUPTED`），工作台返回前台会终止遗留 `planning/rendering`。这是在「无后台运行能力」前提下的诚实兜底，本任务引入真实后台运行后需要条件化，而不是删除。

## 三、调研结论（选型依据，含来源）

1. **specialUse 前台服务**是本地分发 APK 的最优解：无运行时前置权限、**不受 Android 14/15 的 6 小时超时限制**（该限制只约束 `dataSync`/`mediaProcessing`）。`PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 说明文本仅在 Play 审核时被读取；本项目走官网分发，无政策约束，但仍如实填写。
2. **FGS 的豁免边界**：豁免进程冻结、App Standby、后台回收；**不豁免 Deep Doze**。Deep Doze 中只有电池优化白名单应用保留网络 + WakeLock。
3. **PARTIAL_WAKE_LOCK** 在「熄屏但未进入 Deep Doze」（随身携带、充电、亮屏）场景下有效保 CPU。充电状态 Doze 完全不触发。
4. **电池优化白名单**：`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（normal 权限）+ `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` intent 弹系统确认框；拒绝后兜底跳 `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`（列表页）/`ACTION_APPLICATION_DETAILS_SETTINGS`（应用详情页）。系统对话框必须用户手动确认，无法绕过（这是系统行为，与分发渠道无关）。
5. **POST_NOTIFICATIONS**（Android 13+ 运行时权限）：拒绝后 FGS 仍运行并出现在任务管理器，但通知抽屉不显示。需要在设置页提供状态与请求入口。
6. **Capacitor 生态选型**（已核实插件 v8.1.0 源码与文档）：
   - 采用 `@capawesome-team/capacitor-android-foreground-service@8.1.0`（MIT，活跃维护，兼容 Capacitor 8）：提供 FGS 启动/更新/停止、通知渠道管理、`POST_NOTIFICATIONS` 的 checkPermissions/requestPermissions；其服务 `AndroidForegroundService` 返回 `START_STICKY`，通知 `contentIntent` 直接拉起 App 主界面（已读源码确认）。
   - **specialUse 集成方式**（源码级确认）：插件 TS 枚举只有 `Location`/`Microphone`，但 `onStartCommand` 在未传 `serviceType`（=0）时调用**双参** `startForeground(id, notification)`，系统将使用**清单声明的服务类型**。因此只需在 App Manifest 里把插件服务声明为 `android:foregroundServiceType="specialUse"` 并附 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 属性，运行时不传 `serviceType` 即可——无需传未定义的枚举值。
   - **插件不持有 WakeLock**（源码确认）：熄屏后 CPU 仍可能休眠。Capacitor 生态没有维护中的 PARTIAL_WAKE_LOCK 插件（`@capawesome/capacitor-keep-awake` 只是保持亮屏，不适用），因此需自写极小的 Kotlin 补件。
   - **插件无电池优化 API**：`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 引导（含三级兜底）也放入同一个自写小插件，逻辑直接借鉴 Android-web `ShellSessionController`。`@capacitor/background-runner`（15 分钟节拍）不适用。
   - 遵循「同一能力只引入一个统一库」原则：FGS 能力 = capawesome 插件（唯一新依赖）；WakeLock + 电池引导 = 无成熟库，按仓库现有 50+ 手写插件模式做最小自写（单一文件、职责清晰）。

## 四、方案架构

### 4.1 总体设计

新增 **TaskGuard（任务护持）机制**：TS 业务层在长任务开始时通过 capawesome 插件启动 specialUse 前台服务（常驻通知），同时经自写小插件持有 `PARTIAL_WAKE_LOCK`；任务到达终态后释放 WakeLock、停止服务。服务与补件是纯机制载体（启停、通知、WakeLock、电池优化跳转），**何时启停由 TS 业务层决定**，符合「Kotlin 不决定业务流程」的硬规则。

```
TS 编排层 (standalone-production-service / 采集 / 拆解 / 观察)
   │ withTaskGuard(kind, fn)              ← 业务决策在此层（引用计数，多任务并存）
   ▼
task-guard-client.ts (packages/capacitor-runtime)
   ├─ ForegroundService.startForegroundService({id,title,body,channel})   ← @capawesome-team 插件
   │     └─ AndroidForegroundService (specialUse, START_STICKY, 通知点击拉起 App)
   └─ TaskGuardPlugin.holdWakeLock(kind) / releaseWakeLock(kind)          ← 自写最小 Kotlin 补件
         ├─ PARTIAL_WAKE_LOCK 引用计数（kind 为键，归零释放）
         ├─ getBatteryOptimizationStatus / requestIgnoreBatteryOptimizations（三级兜底）
         └─ setBackgroundRunEnabled(boolean)（后台运行开启时不做亮屏保持）
```

启动/停止时序：任务开始 → `startForegroundService`（首次）+ `holdWakeLock` → 任务推进（熄屏/切后台继续）→ 任务终态（含失败/取消）→ `releaseWakeLock`（最后一个释放时）+ `stopForegroundService`。进程被杀时服务与 WakeLock 随进程消亡；`START_STICKY` 只重启空服务进程，编排链回落现有幂等中断恢复。

### 4.3 与现有机制的协同调整

1. **ActiveWorkScreenStay（亮屏保持）**：后台运行开启时不再 acquire `FLAG_KEEP_SCREEN_ON`（让屏幕自然熄灭，任务由 TaskGuard 续跑，显著省电）；后台运行关闭时保持现状。TS 层在任务启动/偏好变更时调用 `TaskGuardPlugin.setBackgroundRunEnabled` 设置内存策略位，`ActiveWorkScreenStay.apply` 查询该位分流；Kotlin 不读取业务偏好存储。
2. **通知（web 层任务通知）**：现有任务通知体系不受影响；FGS 通知是独立系统通知（capawesome 插件管理，`ongoing=true`，点击经 `contentIntent` 直接拉起 App，无需悬浮窗权限）。
3. **进程被杀兜底**：`START_STICKY` 只恢复 Service，不恢复 WebView 编排链。进程重建后仍走现有「幂等中断恢复」，与当前行为一致——TaskGuard 把「被杀概率」大幅降低，但恢复语义保留。已知插件边界：被杀重启时 `onStartCommand` 收到 null intent，插件源码会走异常捕获分支且不再重建前台通知（服务空转）——本项目 TS 客户端在冷启动时不依赖服务存活，该边界不影响正确性，如实记录。
4. **真实性约束**：设置页状态行只显示 `isIgnoringBatteryOptimizations`、通知权限、活跃护持计数三项**实测状态**；不显示「已保活✓」这类无法证实的断言；引导文案说明「绝大多数场景可后台续跑」，不承诺绝对。

### 4.4 电池优化引导流程（借鉴 Android-web `ShellSessionController`）

```
设置页「电池优化」行
  ├─ 状态 = isIgnoringBatteryOptimizations(packageName) 实时读取
  └─ 点击「去设置」：
       1. 先发 ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS + package: Uri（系统确认框，一步到位）
       2. ActivityNotFoundException 时兜底 ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS（列表页）
       3. 仍失败兜底 ACTION_APPLICATION_DETAILS_SETTINGS（应用详情页）
       4. 返回 App 后重读状态刷新显示（onResume 触发 getStatus 重查）
```

## 五、任务契约（按模板）

### 目标
- 用户可感知的结果：一键制作/采集/拆解/观察运行中，熄屏或切后台任务继续推进，返回前台看到任务仍在运行或已完成；设置页可开关后台运行、查看并引导电池优化白名单与通知权限。

### 允许修改
- `apps/web/package.json`（新增 `@capawesome-team/capacitor-android-foreground-service` 依赖）
- `android/app/src/main/java/com/hongtai/aiagent/`（新增 bridge/TaskGuardPlugin，修改 MainActivity、Manifest、ActiveWorkScreenStay）
- `packages/capacitor-runtime/src/`（task-guard-client、standalone-production-service、standalone-app-runtime、runtime-interruption 消费方）
- `apps/web/src/`（SettingsPage、background-run-preferences、受影响测试）
- `docs/`（本任务文档、当前能力与发布状态、架构与工程规范如需）

### 明确不做
- 不引入云后端、登录、同步；不申请 `CAMERA`、相册类或 `MANAGE_EXTERNAL_STORAGE` 等宽泛权限（仅新增本文列出的 4 个 FGS/通知/电池权限）
- 不做「无限保活」：任务终态即停服务、释放 WakeLock；空闲时无任何常驻组件
- 不修改 Pipeline 业务规则、Schema、平台解析逻辑
- 不处理 OEM 厂商自建休眠的代码级豁免（做不到，只做设置引导文案）
- Kotlin 不读取业务偏好、不决定业务流程

### 架构归属
- 所属层：Android I/O（插件机制与策略位）+ capacitor-runtime（任务接线）+ Web UI（设置页）；FGS 生命周期由第三方插件承载
- 依赖方向：UI → AppRuntime DTO → capacitor-runtime（task-guard-client）→ capawesome ForegroundService 插件 / TaskGuardPlugin；禁止 Kotlin 反向决定业务

### 权威状态与数据
- TaskGuard 活跃计数为进程内权威（single source）：TS 客户端维护活跃 kind 集合，首个启动 FGS、末个停止；WakeLock 计数在 Kotlin 侧按 kind 同步计数，两侧对账（异常兜底：TS 侧 stop 一定调用，Kotlin 侧 release 幂等容错）
- `projectId`/`taskId` 状态权威不变（现有落盘机制）；TaskGuard 只是进程存活保障，不写任务状态
- 后台返回不再触发 `TASK_INTERRUPTED` 的前提：TaskGuard 活跃计数 > 0 且进程未重建（运行期内存事实），而非「曾经启动过」

### 验收
- 定向测试：Kotlin 单测（WakeLock 计数、电池优化 intent 构造可测部分）；TS 测试（withTaskGuard 生命周期：成功/异常路径均释放停止、偏好关闭时 no-op、中断语义条件化、设置页状态渲染）；`pnpm check`；`pnpm --filter @hongtai/web build`
- Android：Gradle 测试 + `lintRelease` + Release 构建（`scripts/build-android-release.ps1`），归档 `HongTai-AI-Agent-release-v0.1.28.apk`

## 七、风险与边界（诚实声明）

1. **Deep Doze 不可完全豁免**：熄屏 + 静置 + 未充电约 30 分钟后，即使 FGS + WakeLock + 白名单也可能进入受限窗口。文案写「绝大多数场景」，建议长任务插电运行。
2. **国产 ROM 变数**：MIUI/ColorOS 等有自建激进休眠，标准 API 无法豁免；设置页提供引导说明，不做虚假承诺。
3. **START_STICKY 不恢复编排链**：进程被强杀后 Service 自动重启，但 TS 管线链断——回落现有幂等中断恢复（提示重试），这与现状一致，只是触发概率大幅下降。
4. **JS 定时器节流残余风险**：管线为事件驱动 await，风险低；P2 实施时审计管线全链路 `setTimeout` 使用点（重试退避等），关键路径改为事件/回调驱动。
5. **WebView 后台 binder 流量**：后台期间 JS 不做高频轮询（现有 progress 为事件推送，符合）；P2 审计确认无每秒级 bridge 轮询。
6. **权限面扩大**：新增 4 个权限均为 normal 级（POST_NOTIFICATIONS 为运行时请求，用户可拒且服务仍运行）；已在设置页如实展示状态。
7. **插件集成专项风险（P1 spike 消除）**：① specialUse 经清单声明 + 不传 serviceType 的路径已读 v8.1.0 源码确认，但需 API 34/35 模拟器实测 `MissingForegroundServiceTypeException` 不出现；② 插件通知未设 `FOREGROUND_SERVICE_IMMEDIATE`，Android 12+ 首次通知可能延迟约 10 秒显示（纯视觉、可接受）；③ 插件升级可能改变 onStartCommand 行为——锁定 `8.1.0` 精确版本并在 `pnpm-lock` 固化。
