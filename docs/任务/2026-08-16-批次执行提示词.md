# 修复批次执行提示词

> 定稿：2026-08-16。配套 [修复批次执行总纲](2026-08-16-修复批次执行总纲.md)。
>
> 本文是提示词库。总纲回答「按什么顺序做、谁改什么、怎么验证」，本文回答「怎么把一个批次交给一次 Cursor 对话」。

## 用法

一个批次 = 一次全新的 Cursor 对话。开新对话，复制对应批次的提示词块，粘贴，发送。中途不要在同一对话里切换批次。

批次之间的顺序约束见总纲：批次 1 必须最先做，批次 7 建议最后做，其余可自行排序。

## 编排模型

### 为什么用子代理

Cursor 的子代理各自持有独立的上下文窗口，**只有最后一条消息回到主线程**，中间读过的文件、跑过的命令输出、走过的弯路全部留在子代理里，随子代理一起丢弃。所以子代理的价值不是并行提速，而是把「读得宽、报得窄」的脏活挡在主线程之外。

这决定了本轮的分工：主线程只做编排和裁决，它的上下文里只应该出现 Issue 编号、子代理的结论、验证命令的退出码和 commit SHA，不应该出现实现代码。实现同样交给子代理——串行地交。

### 为什么是串行

`AGENTS.md` 规定本项目只在仓库根目录工作，禁止创建 Git worktree 或复制式隔离工作区。禁的是并行改代码，不是禁子代理改代码。串行跑写代理既满足这条规则，又保留了上下文隔离的全部收益。

**硬约束：任何时刻只允许一个会写文件的子代理在运行。** 只读子代理可以并行。

### PDCA 与 sub-issue 的映射

一个 sub-issue = 一个完整循环，四个阶段各对应一次子代理派发或一次主线程动作：

| 阶段 | 执行者 | 产出 |
| --- | --- | --- |
| P 计划 | 只读子代理 | 复核 Issue 描述是否仍成立 + 最小改动方案 + 影响面 |
| D 执行 | 可写子代理（独占） | 实现 + 测试 + 定向测试结果 |
| C 检查 | 主线程亲自跑验证 + 只读复查子代理 | 退出码 + 越界与回归清单 |
| A 处置 | 主线程 | 通过则 commit；不通过则派新的写代理返修 |

C 阶段主线程必须**亲自**跑验证命令，不接受写代理自述「测试已通过」。这是本轮唯一不允许委派的动作。

A 阶段返修时**派新的写代理**，不复用 D 阶段那个。带着错误推理的上下文继续修，通常会修出第二个问题。

## 通用执行协议

各批次提示词引用本节。以下规则对全部批次生效。

### 主线程纪律

1. 不通读实现代码。需要理解某段代码时派只读子代理，让它返回结论而不是代码。
2. 不在主线程贴大段 diff、日志或文件内容。
3. 每完成一个 sub-issue 立刻 commit，不攒到最后。
4. 一次只推进一个 sub-issue，完整走完 PDCA 再开下一个。

### 子代理派发纪律

子代理是**冷启动**的，拿不到你和用户的任何对话历史，也拿不到之前子代理的结论。派发提示词必须自带全部必要上下文：分支名、Issue 编号、允许修改的目录、验证命令、以及上一阶段的结论。

每次派发必须指定返回格式，且要求「返回结论不返回代码」。子代理的返回值也会占用主线程上下文，一份啰嗦的报告和自己读文件的区别不大。

### 阶段派发模板

**P 阶段（只读，可与同批其他 sub-issue 的 P 并行）**

```
只读复核任务。不要修改任何文件。

仓库：D:/projects/Dev-Tools/HongTai-AI-Agent，分支 <BRANCH>。
先读 AGENTS.md 与 docs/架构与工程规范.md。

目标 Issue：#<N>。用 `gh issue view <N>` 读取正文。
该 Issue 写于 2026-08-16，基线是 main 的 47b7b2d。请对当前 HEAD 复核。

按以下格式返回，全文不超过 40 行，不要粘贴代码块：
1. 结论：仍成立 / 部分成立 / 已不成立（一句话理由）
2. 涉及文件：路径 + 行号范围，每条一行
3. 最小改动方案：分条，每条一句
4. 影响面：会被这次改动影响的调用方与测试文件
5. 风险：跨层越界、并发写入、生命周期、真实性四类里命中哪些
```

**D 阶段（可写，同一时刻只能有一个）**

```
实现任务。你是当前唯一被允许写文件的代理。

仓库：D:/projects/Dev-Tools/HongTai-AI-Agent，分支 <BRANCH>。
先读 AGENTS.md 与 docs/架构与工程规范.md，严格遵守其中的分层与安全规则。

目标 Issue：#<N>。用 `gh issue view <N>` 读取正文与验收标准。
允许修改的目录：<DIRS>。跨出该范围请先停下并说明理由。

已完成的复核结论：
<把 P 阶段返回的第 2、3、4 条原样粘贴到这里>

要求：
- 只做这一条 Issue，不顺手修别的问题。
- 补齐能覆盖该缺陷的测试；测试必须在修复前会失败。
- 完成后运行 <VERIFY_CMD>，把结果如实报告，失败就说失败。
- 不得为了让测试通过而放宽断言、跳过用例或关闭检查。
- 不要 commit，交给主线程处理。

按以下格式返回，全文不超过 30 行：
1. 改了哪些文件，每个文件一句话说明改了什么
2. 新增或修改的测试，以及它们验证的行为
3. 验证命令的真实退出码与失败摘要
4. 未解决的遗留问题
```

**C 阶段（只读复查）**

```
只读复查任务。不要修改任何文件。

仓库：D:/projects/Dev-Tools/HongTai-AI-Agent，分支 <BRANCH>。
先读 AGENTS.md 的「Code Review Rules」一节。

用 `git diff` 查看当前未提交的改动，它对应 Issue #<N>。
用 `gh issue view <N>` 读取验收标准。

重点检查：跨层越界导入、并发覆盖、生命周期缺终态、密钥或原始响应泄漏、
真实性（假进度/假成功/fixture 冒充真实结果）、UTF-8 与 U+FFFD。

按以下格式返回，全文不超过 25 行：
1. 验收标准是否逐条满足（逐条列出，满足写「是」，否则说明差在哪）
2. 发现的问题：文件 + 行 + 触发条件 + 最小修复方向，每条不超过三行
3. 是否可以提交：可以 / 需返修
只报告本次改动引入的、可复现的问题，不要报格式与通用 lint。
```

### 停止条件

出现以下情况停下来问用户，不要自行推进：

- P 阶段判定 Issue「已不成立」——记录证据，跳过该条，在 PR 正文里说明，不要硬改。
- 修复需要做产品决策（改变用户可见行为、改变医疗边界措辞、改变发布口径）。
- 改动必须跨出该批次允许的目录，且不是显然的连带修改。
- 同一条 sub-issue 返修两次仍未通过复查。

### 收尾

全部 sub-issue 完成后：

1. 主线程跑一次该批次的完整验证（见总纲「验证映射」）。
2. 派一个只读子代理对**整批 diff**（`git diff origin/main...HEAD`）做一次防回归复查。
3. 推送分支，创建 PR。PR 正文包含：变更摘要、每条 sub-issue 的测试证据（命令 + 结果摘要，不接受只写「已测试」）、风险与回滚思路、末尾列出全部 `Closes #NNN`。
4. 未经用户明确授权不得合并。
