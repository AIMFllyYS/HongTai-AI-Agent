# 2026-09-01 B 站解析 WBI 签名修复

## 明确不做

- 不改 Android 原生网络/下载/remux 代码（#122 音频槽 MIME 修复已自 v0.1.19 在包内，本次实测 CDN 音频仍声明 `video/mp4`，该修复继续有效）。

## 架构归属

- 所属层：`packages/platforms`（B 站适配器）。
- 依赖方向：只用已有 `HttpClient` 契约与既有 `signWbiQuery`/`wbiKeysFromNav`；不导入 Node/浏览器/Capacitor API；Kotlin 侧零改动。

## 根因（系统性结论）

1. **直接根因**：B 站把未签名的 `x/web-interface/view` 纳入风控——同 IP 同时刻实测：未签名 `view` 必返 HTTP 412（HTML 验证页），而 WBI 签名的 `x/web-interface/wbi/view` 返回 200 完整 JSON。适配器恰好只用未签名 `view` 取元数据（playurl 此前已签名），于是 parse 阶段（七阶段之「提取内容」）整体失败。
2. **为什么「修过很多次仍不好使」**：#87 修的是整页 HTML 与 playurl 签名，#122 修的是音频槽 MIME，都正确但都没碰到 view 端点；且 412 按 IP/频次触发，主机探测时可能恰逢未风控，造成「CLI 好使、手机不好使」的假象——本次实测同一被拒 IP 下 CLI 与 curl 同样 412，手机端（移动网络 + 无浏览会话）只是更容易触发。
3. **验证矩阵**（本机、已触发 412 的 IP、全程无 Cookie）：`b23.tv/dRtdz4d` 302 正常；`nav` 200（-101 未登录但含 `wbi_img`）；`pagelist` 200；未签名 `view` 412；**WBI `view` 200**（bvid/aid 均可）；WBI `playurl` 200（DASH 4 视频 + 3 音频）；CDN 双流 HEAD 200（音频 Content-Type 仍为 `video/mp4`）。

## 修复

- `parse` 先取 WBI 密钥（匿名 `nav` 接口，未登录也返回），有密钥时 view 走 `x/web-interface/wbi/view` 签名请求；`nav` 失败时退回原未签名端点，行为不变。playurl 逻辑不变（复用同一份密钥，少一次 `nav` 请求）。
