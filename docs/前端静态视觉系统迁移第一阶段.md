> 状态：第一阶段执行基线（静态视觉与前端结构，不代表真实业务链路已接通）

>
> 设计资产：`D:\projects\Dev-Tools\HongTai-AI-Agent\docs\Hong`

## 1. 范围与结论

本阶段的目标是把 Stitch 设计资产中的用户端视觉语言迁入当前仓库，建立后续可以替换真实 CLI/应用层的 TypeScript 前端边界。当前仓库本身没有 Web 前端、React 组件、路由、状态库或请求层，因此本次迁移采用最小增量：新增独立的 `apps/web` Vite + React + TypeScript 应用，复用现有 `packages/core` 的稳定类型语义，但不修改核心业务实现。

本阶段只交付：

- 设计资产、Stitch 屏幕和现有项目约束的审查记录；
- `apps/web` 的共享 token、应用壳、导航、通用卡片/状态/输入组件；
- 代表主工作流的静态页面骨架与真实可访问 route；
- `VisualDataAdapter` 可替换展示边界和一套本地静态 fixture；
- 构建、类型、Lint、现有测试、浏览器截图和视觉差异记录。

本阶段明确不做：

- 真实 CLI/API/DTO/数据库/鉴权/价格/积分/配额/任务状态机接入；
- 修改 `apps/cli`、`packages/core`、`packages/platforms`、`packages/ai`、`packages/node-runtime` 的逻辑；
- 新建 Android/Capacitor 工程；
- 把 Stitch 远程资产上传、修改、应用到远程项目；
- 把 HTML 中的脚本、Tailwind CDN 或远程字体依赖原样带入应用；
- 为未定义的业务规则、真实状态和接口字段做推断。

### 2.2 已确认规范

- 根目录使用 pnpm workspace、ESM 和 TypeScript strict 模式；`tsconfig.base.json` 开启 `strict`、`noUncheckedIndexedAccess`、`verbatimModuleSyntax` 和 `isolatedModules`。
- 根检查命令为 `pnpm check`，实际顺序是全 workspace typecheck、ESLint、`tsx --test tests/*.test.ts`。
- `packages/core`、`packages/platforms`、`packages/ai` 禁止导入 Node 模块；前端不能把 Node 运行时能力反向带入共享层。
- 核心契约已经定义了 `PlatformContent`、`ProgressEvent`、`TaskRecord`、`TaskIssue`、`IngestResult`、`inspectInput` 和七个 `TaskStage`。
- 现有文档明确指出正式 React/Capacitor 页面尚未实现，CLI 只是开发期无界面入口；这意味着前端只能作为新的用户端消费层，不能假装已有页面路由。
- 中文文件和源码必须保持 UTF-8。新增文档和 TypeScript 源码使用 UTF-8，不在 PowerShell 中用系统代码页重写中文文件。

### 2.3 前端不可越过的边界

静态页面可以展示设计稿中的分析、制作、素材、设置和图片观察视觉，但所有内容仅属于 view model/fixture。未来真实接入必须由 adapter 将 `TaskRecord`、`ProgressEvent`、`IngestResult`、`DiagnosisReportV1` 等正式结果映射到 view model；页面不得读取 CLI 文件、解析中文错误、猜测未定义状态或直接调用 Node API。

现有错误通知约定要求前端按稳定 `TaskIssue.code`、`severity` 和 `action` 展示通知，不能依赖 `userMessage` 字符串判断业务类型。本阶段只建立展示组件的状态入口，不实现真实错误流转。

### 5.2 组件规则

- `AppShell` 统一处理安全区、页头、内容底部留白和移动端底部导航；通过 `backPath` 表达详情返回关系，通过 `showNav` 保留后续关闭导航的能力。本阶段所有页面保留统一底部导航，未引入第二套页面壳。
- `BottomNav` 统一五项视觉和 route 映射；“AI”入口和“拆解”入口的业务关系尚未在现有核心中定义，现阶段只按设计资产提供可访问静态入口。
- `GlassCard` 负责白色/半透明卡片、边框、圆角和柔和阴影；页面不自行复制这些值。
- `StatusBadge` 只接受显式 status，不通过中文文案猜状态；`ProgressSteps` 只接受 `TaskStage`/`StageStatus` 的 view model。
- `EmptyState`、`LoadingState`、`ErrorState` 使用同一视觉语气和 icon+text 结构；不伪造真实错误请求或任务重试。
- `Button` 通过 `primary`、`secondary`、`ghost`、`quiet` variants 统一高度、focus ring、disabled 和按压态；按钮行为仅做静态导航或本地视觉切换。
- `MediaFrame` 对远程/缺失资源提供渐变 fallback，避免设计稿中破图导致布局坍塌；不把外部图片当作可靠业务数据。

### 5.3 响应式与可访问性

- 移动端优先，目标参考尺寸 390–420px 宽，桌面/平板在 780px 内容宽度内增加列数；不复制截图的固定高度。
- fixed bottom nav 必须预留 `env(safe-area-inset-bottom)`；页面主内容必须有足够 `padding-bottom`，不被导航覆盖。
- 所有 icon-only 按钮提供 `aria-label`；状态图标不单独承载语义；输入和按钮保持键盘 focus 可见。
- 所有远程/装饰图提供 alt 或 `aria-hidden`；所有页面有唯一 h1；tabs 使用 button 和 `aria-selected`。

## 6. 不确定项与冲突项

1. 当前仓库没有前端实现，因此 route 名称、页面壳和 adapter 是本阶段新增约定，不应被误认为已有产品合同。
2. Stitch 的设计文档写的是四项 bottom navigation，而本地 HTML/PNG 和 Stitch screen 视觉都出现五项（额外的“AI”入口）。本阶段保留五项以还原资产，并在后续真实产品导航决策前不删除任何项。
3. `Profound Logic AI` 和 `Warm Soft Tech` 对正文/标签字体、页面边距、圆角和 primary/secondary 色值有差异。本阶段以 `Profound Logic AI` 作为主工作台基线，在 Vitality 页面局部使用 `Warm Soft Tech` 变量；若未来要求统一品牌，需要单独设计决策。
4. HTML 的 `img`、字体和 Tailwind CDN URL 是外部资源，无法证明在未来 APK 离线环境可用。新应用不依赖它们，截图中的照片使用可替换媒体源和 CSS fallback；真实素材缓存/打包另行确定。
5. 设计稿中的“AI 诊疗/健康评分/咨询专家”语义与现有文档中“图片可见状态观察、不是疾病诊断”有关联但没有前端正式业务合同。本阶段只做静态视觉占位，不新增医疗结论、健康规则或专家服务链路。
6. 设计稿中的进度百分比、模型名称、PRO 账号、点赞数和发布时间都是示例内容，不能进入真实任务/账号/计费状态。
7. “保存并去发布”“咨询专家”“继续优化”等按钮的真实系统唤起和权限流程未定义，本阶段只允许前端导航或无副作用的静态状态切换。

## 7. 后续真实接口依赖与建议顺序

真实接入前需要先确定正式 repository/adapter 接口和响应生命周期，建议顺序为：

1. 先接输入检查：复用 `packages/core` 的 `inspectInput`，把 `InputInspection` 映射到输入预览/错误状态；
2. 再接任务创建与事件订阅：把 `TaskRecord`、`ProgressEvent`、`TaskIssue` 映射到处理页和状态组件，保持七阶段状态语义；
3. 接入任务产物读取：把 `IngestResult`/产物索引映射到视频、文稿、图文详情和结果页，不让页面读取 `workspace`；
4. 接入内容拆解：以 `content-analysis.v1` 和真实证据引用为源，替换静态钩子/价值/正文/CTA view model；
5. 接入本地素材/模板 repository：先定义缓存、缩略图、上传失败和重试边界，再替换素材库/制作页 fixture；
6. 接入 AI 配置展示：只显示已定义的配置状态和安全脱敏字段，不在前端保存或记录 API Key；
7. 最后再确定 Android/Capacitor 文件、媒体、分享和端侧 AI 能力，不把 Web 静态页面误当成原生媒体引擎。
